# Architecture

- `apps/api`: NestJS REST API, Prisma ORM, JWT auth + permission guards (Phase 2), Swagger at `/api/docs`.
- `apps/web`: Next.js App Router, Tailwind, TanStack Query/Table, React Hook Form + Zod. shadcn/ui components are added via its CLI per phase.
- `packages/costing-engine`: pure, tested decimal calculation logic shared by API (authoritative) and web (preview).
- `packages/types`, `packages/validators`: shared types and Zod schemas.
- `prisma/schema.prisma`: single schema; Phase 1 contains only `User`. Models are added per phase.

Phase 1 delivers the skeleton only. Next: Phase 2 (auth, users, permissions).

## Phase 2: Authentication & permissions
- Login returns a 15 min JWT access token; a rotating 7 day opaque refresh token lives in an httpOnly cookie (hash stored in `Session`). Logout, password reset/change and deactivation revoke sessions.
- Permissions are `<module>:<action>` rows (22 modules × 10 actions, defined in `@costing/config`). Effective permissions = role grants + per-user ALLOW − per-user DENY; super admins hold everything.
- `JwtAuthGuard` and `PermissionsGuard` are global. Routes are private by default; use `@Public()` to opt out and `@RequirePermission(module, action)` to protect. Live DB lookup per request means role/permission changes apply immediately.
- Audit log records login, user/role changes and permission edits.
- Forgot password: no mail transport yet; the reset token is written to the API log (wired to email in the Settings phase).
- First admin: set `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD`, then `pnpm db:seed`. The admin must change the password at first login.

## Phase 3: Master data
- Nine masters (types, item groups, categories, units, suppliers, labour, expenses, conversions, items) share one config-driven CRUD stack: `apps/api/src/masters/masters.config.ts` declares each master (Zod schema from `@costing/validators`, search/filter/sort fields, includes, referencing models, extra validation); `createMasterController` builds the REST routes and `MasterService` the logic. Permission modules map 1:1 (`types:view`, `items:edit`, …).
- Validation is the same Zod schema on the API (authoritative) and in the web forms.
- Deleting is a soft delete (`deletedAt`) and is refused with 409 while active records still reference the master; the code/symbol is suffixed so it can be reused. Deactivation is the reversible alternative.
- Hierarchy is enforced server-side: group must belong to the item's type, category to its group.
- Items: base unit + per-item unit conversions (`1 Meter = 3.15 KG`), per-supplier rates with one default, and an optional Min/Max/Average block that is only stored when "capable for Min/Max/Average" is on (otherwise the standard rate applies). The average itself is computed from purchases in Phase 4.
- Units carry a `baseFactor` for generic same-type conversion; `convertQuantity` in `@costing/costing-engine` uses item conversions first, then generic factors, and throws for incompatible units. Generic conversion rules across different unit types are rejected unless tied to an item.
- `pnpm db:seed` also seeds starter units (KG, Gram, Meter, Feet, Inch, Sq Ft, Litre, ML, Piece, Box, Set).
- Web: one `MasterPage` (search, filters, sort, pagination, status, drawer form with dependent selects and nested row editors) driven by `apps/web/src/lib/masters.tsx`; routes at `/masters/<name>`.

## Phase 4: Purchase & rate management
- `PurchaseRate` = one purchase (item, optional supplier, unit, qty, rate, date, reference). Each entry is normalised to the item's base unit (`baseRate`, `baseQuantity`) using the item's unit conversions, so mixed-unit purchases (per metre vs per kg) compare correctly. Incompatible units are rejected.
- `computeRateStats` / `selectCurrentRate` (`@costing/costing-engine`) produce min, max, simple and weighted average and the "last" rate. After every create/delete/import the item is recalculated in the same transaction: Min/Max/Avg are stored only for items flagged capable; the current rate follows the item's rate method (last purchase by default, weighted/simple average, or Manual which never moves automatically). Items without the flag always use the latest purchase.
- The supplier-wise rate on `ItemSupplier` is that supplier's latest purchase.
- `PurchaseRateHistory` is an append-only log of every change to an item's current rate (old/new, min/max/avg snapshot, source PURCHASE / PURCHASE_DELETED / MANUAL / IMPORT, who, when, reason, measured impact). Manual overrides need `purchase_rates:manage_rates` and a reason.
- **Impact workflow**: `RateImpactService` is a registry. Modules that depend on item rates (live costings, price lists, quotations) register a provider; the preview endpoint (`GET /purchase-rates/items/:id/impact?newRate=`) and each history row use it. No such modules exist yet, so impact is currently 0. Phase 6 / 14 / 8 / 9 register providers and implement the actual recalculation, flagging, and the Live vs Snapshot costing policy (a per-document setting in Phase 15). Nothing in this phase touches approved or snapshot documents.
- **Excel**: template, export (formatted, formula totals), and import with preview. Rows are validated (unknown item/supplier/unit codes, bad numbers, future dates, units without conversion) and duplicates (within the file or already recorded) are flagged. Confirm refuses the whole file if any row has a problem unless the user explicitly chooses to skip invalid rows. Every import is recorded in `ImportHistory`.
- Items, suppliers and units that have purchase entries can no longer be deleted (deactivate instead).
- Web: `/purchase-rates` with tabs Rate Summary (with per-supplier rates), Purchase Entries (add/delete, import/export), Rate History (filters), Rate Change Impact (preview + apply).

## Phase 5: Template management
- A template is a reusable costing starting point: type → groups → categories → items (with default quantity, unit, optional per-item wastage), labour per group (quantity, unit, optional rate override; blank = master rate when costing), expenses (whole product or one group, optional method/value override), plus default wastage, GST and markup percentages. Wastage can also be set per group and per category.
- The whole tree is saved in one transaction (`PUT /templates/:id` replaces the tree). Server checks beyond Zod: the type exists, each group belongs to the template's type, each category to its group, each item to its category, units convertible to the item's base unit, labour/expense exist, no duplicates.
- **Versioning**: every save increments `version` and stores a full snapshot in `TemplateVersion` (`GET /templates/:id/versions[/n]`).
- **Costings never change when a template changes**: a costing copies a template's data at creation (Phase 6). Deleting a template is a soft delete; archived templates are read-only and can be restored.
- Duplicate creates an independent copy with a new name/code (version 1).
- Master deletion guards now also cover template usage (types, groups, categories, items, units, labour, expenses) and ignore lines of deleted templates.
- `TemplatesService` is exported for Phase 6 ("create from template", "save costing as template").
- Product reference images are deferred to Phase 10 (image management).
- Web: `/templates` (search, type/status filters, duplicate, archive/restore, delete) and `/templates/new|:id` (nested editor with dependent selects, per-group labour, expenses, version history).

## Phase 6: Costing module (with the calculation core of Phase 7)
- **Engine** (`@costing/costing-engine/costing.ts`): `calculateCosting(input, rules)` is pure and Decimal-only. Rules are explicit (`CalcRules`): decimals and rounding mode, round lines vs totals, GST-inclusive/exclusive rates for material/labour/expenses (converted to ex-GST first so GST is never counted twice), costing-level vs item-level GST, wastage mode, markup base (basic cost or cost incl. GST) and profit base. `resolveWastagePercent` applies the most specific level (item → category → group → overall) or, if configured, adds all levels. `resolveMaterialRate` picks Standard / Min / Max / Average / Supplier / Custom and scales it to the row's unit (falling back to Standard when the figure does not exist).
- **Backend is the only place that calculates**: `POST /costings/preview` and every save run the same `prepare()`: hierarchy validation (shared with templates), master rate resolution, engine. Client-sent rates are ignored except explicit CUSTOM overrides, which need `costing:manage_rates` (previously stored overrides stay). The editor does no money maths; it shows the server preview (debounced) including per-row rates/totals and a calculation breakdown.
- **Rules**: `CostingSettings` (single row, defaults in `DEFAULT_RULES`; `GET/PUT /costing-settings`, settings UI in Phase 15). Each costing stores the rules it was calculated with.
- **Costing** = header (number `COST-<year>-<seq>`, product, dimensions, quantity, date, preparer, GST/markup/wastage) + group → category → material tree, labour per group, expenses (whole product or group). It owns a copy of everything; templates and masters can change without altering it.
- **Create** from a template (`GET /costings/from-template/:id` prefills; nothing saved until the user saves) or from scratch; **Save as template** converts a costing into a template (defaults only, no prices).
- **Workflow**: Draft → (submit) Pending → Approve (rates frozen: `pricingMode` SNAPSHOT, locked) or Reject (reason, editable again). Reopening an approved costing needs `costing:approve` and a reason, creates a new version, and returns it to LIVE pricing. Every save/approve/reopen stores a `CostingRevision` snapshot.
- **Live vs Snapshot**: LIVE costings re-read master rates via `refreshRates` (button and API; Phase 14 will invoke it automatically on rate changes). Approved costings are never touched.
- The costing module registers a `RateImpactService` provider, so the Phase 4 rate-change preview now reports "N live costing record(s)" per item.
- Masters used by a costing can no longer be deleted.
- Not yet: product images (Phase 10), print/PDF/Excel for costings (Phase 11), automatic recalculation on rate change (Phase 14), settings screen (Phase 15). Phase 7 will extend the engine tests and rules rather than rebuild them.

## Phase 7: Calculation engine hardening
- `assertValidCostingInput` runs before every calculation and throws `CostingInputError` (mapped to HTTP 400) for negative or non-numeric quantities/rates, percentages above 100, duplicate row ids (which would overwrite each other's results) and expenses pointing at unknown groups. Zod already blocks most of this at the API; the engine no longer relies on it.
- Every material result now carries `netRate` (rate after removing GST) and a human-readable `formula` (e.g. `(20.94 + 0.4188) × 98 = 2093.16`). The preview returns them per row (shown as a tooltip on the line total) together with the rules used, which the editor lists under "Calculation rules in effect", next to the step-by-step breakdown.
- Tests (59 in the engine package): the reference-sheet figures, each rule option, rounding modes, plus seeded randomised invariants over 150 generated costings × 7 rule sets: totals reconcile (basic = material + labour + pre-GST expenses; total = basic + GST + post-GST expenses; selling = total + markup), nothing negative or non-finite, results deterministic, GST-inclusive rates equal the equivalent ex-GST rates, doubling quantities doubles material cost, and wastage is never stacked in most-specific mode. The server path (`CostingsService.prepare`) has its own test reproducing the reference sheet end to end.
- **Demo data** (`pnpm db:seed:demo`, after `pnpm db:seed`): creates the reference sheet's masters, a "Metal Chair General" template and a demo costing. Expected basic cost: 4,126.12 (material 2,326.12 + labour 1,800; GST and markup 0). Not exercised against a live database in this environment.
- **Frontend/backend sharing**: the engine is one package. The server runs it for every preview and save; the browser deliberately does no money maths and displays the server's preview, so the two cannot disagree.
- **Defaults to confirm with the business owner** (all changeable via `PUT /costing-settings`, screen in Phase 15): 2 decimals, half-up, each line rounded; rates entered ex-GST; costing-level GST; most-specific wastage; markup on total cost including GST; profit % measured against basic cost; after-GST expenses excluded from GST and from basic cost.

## Phase 8: Price lists
- **Pricing rules** (`@costing/costing-engine/pricing.ts`, `calculatePrice`): list price = cost base + profit, where the cost base is the approved costing's cost before GST or including GST (admin choice per list) and profit is a percentage of that base (Method A) or a fixed amount (Method B). A maximum caps the list price, an optional "round to nearest" step is applied (never breaking the cap), then a percentage or fixed discount is taken off. The minimum price is a floor on what the customer pays, so a discount can never push the price below it. Results include profit, GST, price excl./incl. GST, effective price (both bases), margin % (profit ÷ price), markup % (profit ÷ cost) and flags (cap applied, minimum applied, discount limited, below cost). Min/max are in the quoted basis (the list's GST treatment).
- **GST treatment** per list: prices exclude GST (GST shown extra), include GST, or no GST. Percent profit scales with the quoted basis, so 20% on cost before GST quoted inclusive equals 20% then GST (differences of one paisa can occur from rounding at different points).
- **Only approved costings** can be priced. Each item copies the costing's figures and version, so a list never changes silently. If the costing is later changed, reopened or deleted, the item is flagged out of date; a list with out-of-date items cannot be activated until "Reprice from costings" is run on the draft. This is how price lists follow rate changes: rate changes alter costings (Phase 14), approved costings are frozen, re-approval bumps the version and the list shows it.
- Lists: Draft (editable) → Active (read-only, revert to draft to edit) → Archived. Number `PL-<year>-<seq>`. Bulk generation prices any number of approved costings with shared settings (`POST /price-lists/generate`); the editor can also add costings and apply list defaults to all rows. The editor shows a server-calculated live preview (`POST /price-lists/preview`); the browser does no money maths.
- **Excel export** is formatted (frozen header, number formats, filters, flags and stale notes in the notes column). **Print / PDF** is a browser print view (`/price-lists/:id/print`); server-side PDF and branded A4 layouts arrive with the printing phase (11).
- Permissions: `price_lists:view/create/edit/delete/export/print`.

## Phase 9: Customers & quotations
- **Customers** are a regular master (generic CRUD stack, `customers:*` permissions); a customer used by a quotation cannot be deleted. A quotation copies the customer's details, so editing the customer later never changes a sent quotation; free-typed customers are allowed.
- **Totals** (`calculateQuotation`): per line `gross = qty × unit price`, minus a line discount (percent or amount); an optional quotation-level discount (percent or amount) is spread over the lines in proportion to their value using largest-remainder rounding so the shares add up to the discount exactly; GST is charged per line on the discounted value; optional grand-total round-off. Every figure is rounded to the configured decimals and totals are sums of the rounded lines, so printed quotations always add up. A GST-by-rate breakdown is produced for printing. CGST/SGST/IGST splitting needs the company state (Phase 15) and is not done yet.
- **Line sources**: custom items (name, price, GST entered), approved costings (price per unit = costing cost before GST ÷ costing quantity plus a profit % that defaults to the costing's markup %, GST from the costing), and items of an *active* price list (effective ex-GST price ÷ costing quantity). Only approved costings and up-to-date price list items can be quoted; the server prices these lines itself.
- **Workflow**: Draft → Pending (submit) → Approved (needs `quotations:approve`) or Rejected; Draft/Approved → Sent; Sent → Approved (customer accepted) / Rejected (declined, reason) / Expired (automatic once the validity date passes; applied lazily on reads); Approved/Sent → Converted (needs an order/invoice reference); Rejected/Expired → Draft by "Revise". Revising a sent or approved quotation needs `quotations:approve` and a reason, bumps the version and revokes share links. Only drafts can be edited, so sent/approved quotations keep the exact prices the customer saw (the figures are stored on the quotation, not read from the costing).
- **Out-of-date detection**: if a costing behind a line is changed, reopened or deleted, the quotation shows "review" and cannot be approved or sent until repriced (draft: "Reprice from sources"). Duplicating a quotation copies the stored figures into a new draft.
- **Sharing**: a revocable read-only link (`/q/<token>`): 32-byte random token, only its SHA-256 is stored, expires after the validity date or a chosen number of days, only for sent/approved quotations, rate limited. The public view omits costs, profit, internal ids and user details. Creating or revoking links is audited.
- **Output**: Excel download and a browser print/PDF view (`/quotations/:id/print`); the branded PDF with company logo, product images and bank details comes with the printing and image phases.
- Numbers `QTN-<year>-<seq>`; default terms text is a placeholder in the editor until company settings exist (Phase 15).

## Phase 10: Image management
- **Where images live**: costings and templates (product details = the costing screen). Quotation lines and price list items show the main image of the costing they come from; costings list shows a thumbnail. Saving a costing as a template links its photos to the template (same files, no copy).
- **Upload pipeline** (`images/image-processor.ts`): up to 10 files per request, 20 per costing/template, 8 MB each. A file is accepted only if it *decodes* as JPEG, PNG or WEBP (checked by content, not by name or MIME type; SVG, GIF, TIFF, animated images and anything unreadable are rejected, with a 50-megapixel limit against decompression bombs). It is then re-encoded: EXIF/GPS and any appended or embedded payload are discarded, orientation is applied, transparency is flattened onto white, converted to sRGB and saved as a compressed progressive JPEG (max 1600 px) plus a 320 px thumbnail. JPEG is used for every output because browsers and PDF libraries all handle it (printing phase). The whole batch is validated before anything is stored; failures clean up their files.
- **Storage** (`FileStorageService`): local disk under `UPLOAD_DIR` (default `./uploads`, never served statically), server-generated keys only (`images/ab/<uuid>.jpg`), validated again on every access, no overwrites. Back this directory up with the database and mount it as a volume in Docker (Phase 20); swap the class for an S3-compatible driver if you need object storage. Original file names are kept only as sanitised display text.
- **Private serving with signed URLs**: images are not public. The API returns links like `/api/files/<id>?v=thumb&exp=…&sig=…` (HMAC-SHA256 over file, variant and expiry, key `FILE_URL_SECRET`, falling back to `JWT_SECRET`) valid for one hour. They work in `<img>` tags, print views and the customer's shared quotation page, cannot be forged or reused for other files or sizes, and expire.
- **Rules**: upload/describe/set-main/delete follow the owner's edit lock (approved or pending costings and archived templates are read-only, so approved documents never change). The first image becomes the main image; deleting the main image promotes the next. Stored objects are deleted when the last link to a file is removed. Duplicate images on the same owner are refused.
- **Permissions**: view = `costing:view` / `templates:view`; upload, edit, delete = `costing:edit` / `templates:edit`. Uploads are rate limited. All actions are audited.
- **Not yet**: the costing *print sheet* with images is built in the printing phase (11); the signed-URL mechanism and the main-image helper are ready for it.

## Phase 11: Import, export and printing
**Excel import** (`/data/import/*`, screen *Data Management → Import Excel*)
- Kinds: types, item groups, item categories, units, suppliers, customers, labour, expenses, items (with unit conversions and supplier rates as compact text such as `M=3.15` / `SUP01=95*`), templates, price lists; purchase rates keep their Phase 4 endpoints. Each has a downloadable template (a header-only data sheet, so nothing sample-like can be imported by accident, plus an instructions sheet).
- Flow: upload → preview → confirm. The preview validates every row with the same Zod schemas and checks as the screens (references resolved by code, hierarchy rules, duplicates against the database and within the file) and lists every problem per row. Confirm re-validates the file and refuses to import anything while problem rows exist unless the user explicitly chooses to skip them. Masters and templates are inserted in **one transaction** (all or nothing); each price list is created in its own transaction. Every import is stored in `ImportHistory` with its skipped rows and reasons (*Import History* screen) and audited.
- Needs `data_management:import` plus `<module>:create`; 5 MB / 5,000 rows per file; .xlsx only.
- Templates: one row per line (MATERIAL / LABOUR / EXPENSE); a template with any bad line is rejected as a whole. Price lists: one row per product; only approved costings.

**Excel export** (`/data/export/*`, *Export Excel*)
- Masters export in the import layout (edit and re-import). Costing summaries, quotation list and purchase rates carry SUM totals as formulas; an individual costing exports as Summary / Materials / Labour / Expenses sheets (line totals as stored by the calculation engine, sums and a labour line check as formulas). Needs `<module>:export`. Price lists and single quotations export from their own screens.

**Printing**
- Company identity (name, address, contact, GSTIN, currency, footer, logo) lives in `CompanySettings` (*Company Settings*), the start of the Phase 15 settings module.
- Layouts: detailed costing sheet (group-wise materials, labour, expenses, summary, product image and dimensions), costing summary, product costing with image, material details, labour details, price list and quotation. Every layout shows the company letterhead, costing/quotation number, date, status, preparer and GST details.
- **On screen**: print preview pages with A4 portrait/landscape (an `@page` rule, so the browser print dialog starts in that orientation), the layout selector, and Print.
- **PDF**: generated on the server with pdfkit (`/print/costings/:id/pdf?mode=&orientation=`, `/print/quotations/:id/pdf`, `/print/price-lists/:id/pdf`) from the same server-calculated data: paginated tables with repeated headers, "Page x of y", logo and product images embedded. Needs `<module>:print`.
- **Limitation to know**: the built-in PDF fonts cover Latin-1 only, so the rupee sign prints as "Rs." (amounts are labelled with the currency code) and non-Latin text (e.g. Devanagari) prints as "?" in PDFs. The on-screen preview and browser printing handle all scripts. Bundling a Unicode font (e.g. Noto Sans) is a deployment-phase task.
- The public share page (`/q/<token>`) now has the company letterhead.

## Phase 12: Dashboard and reports
**Dashboard** (`GET /dashboard`, the home screen): counts of products (distinct product names), costings, templates, suppliers, items, customers, quotations, pending (pending approval + sent) and approved quotations; costings and quotations by status (with quotation value per status); recent costings, rate changes, quotations and activity. Every section is returned only if the user can view the underlying data (costing, quotations, templates, suppliers, items, customers, purchase rates, audit logs), so the dashboard never reveals costs, rates or values to people without access. Hidden sections are not even queried.

**Reports** (`/reports`, grouped like the menu). One definition per report in `reports/report-defs.ts` drives the screen, the Excel file and the PDF, so the three always agree:
1. Product-wise costing · 2. Type-wise costing · 3. Group-wise material cost · 4. Item-wise purchase rate · 5. Supplier-wise rate · 6. Labour cost · 7. Wastage · 8. Profit · 9. Selling price (costing vs active price list vs last quotation) · 10. Quotation (with a by-status summary) · 11. Rate change impact · 12. Costing history (every saved version).
- **Filters** (each report offers the relevant ones): date range, product (name or code), type, group, supplier, item, status. They are validated (dates, ids, status values) and bad input is a 400, never silently ignored; the "to" date includes the whole day.
- **Output**: on screen with totals and paging; Excel with formatted columns, frozen header, autofilter and SUM total formulas; PDF (landscape, company letterhead, applied filters, repeated headers, page numbers); browser Print with the full table. Sums are computed with decimals and returned as strings.
- **Access**: `reports:view` plus view access to the data the report reads (e.g. supplier rates need purchase-rate and supplier view); Excel needs `reports:export`, PDF/print `reports:print`.
- **Limits**: a report refuses to run over more than 100,000 source records (narrow the filters); the screen shows at most 5,000 rows (Excel and PDF contain all). Group-wise and wastage reports derive each line's wastage cost as its share of the line cost, `total × (effective qty − qty) / effective qty`, which is exact whether or not rates include GST.
- Aggregation is done in the application over indexed, filtered queries, which is comfortable at this business's scale; very large databases would move the heavy reports to SQL views (see Phase 13).

## Phase 14: Live recalculation and data integrity
**What triggers it.** A change to anything a costing is calculated from is announced on an in-process `ChangeBus` *after it is committed*: an item's rate (purchase entered / removed / imported, manual rate change, rate edited in the item master), its min / max / average or a supplier's rate, item GST %, item base unit or unit conversions, a labour rate, an expense default (value, method, timing), and the calculation rules. Changes made on the item / labour / expense screens are detected by comparing the record before and after the edit (decimal-aware, so `98` and `98.0000` are the same). A rate edited in the item master now also writes a `PurchaseRateHistory` row, which it did not before. Costing-level wastage, GST and markup are inputs of one costing and are recalculated when that costing is saved; template defaults only affect new costings.

**What gets recalculated.** Only **live** costings (`pricingMode LIVE`) that are draft or rejected. Approved (snapshot) costings are never touched; costings waiting for approval are skipped with a reason so the figures under review do not move. Rows with a custom rate keep it; fields of an expense the user overrode keep their override while the others follow the master (the new `CostingExpense.overrideFields`, backfilled by the migration). A costing whose figures come out identical is not rewritten, so versions are not created for nothing. Recalculating a costing saves a new version with the reason in its history.

**Policy** (*Rate Change Impact* screen, `GET/PUT /recalculation/policy`): *Confirm* (default: a batch waits for an admin), *Automatic* (applied immediately by a permission-less background actor, up to 200 costings, otherwise it waits) or *Manual* (nothing is queued; use "Refresh rates" per costing). Further changes to the same source update the pending batch instead of piling up new ones (enforced by a partial unique index).

**Preview and confirm.** `GET /recalculation/batches/:id/preview` is a dry run that returns before / after selling price per costing, the total change, and what would be skipped. `POST …/apply` (needs `purchase_rates:manage_rates` and `costing:edit`) claims the batch atomically (no double apply), recalculates each costing in its own transaction (one failure never blocks the rest), records every result in `RecalculationItem` and leaves the batch PARTIAL if anything was skipped or failed, so it can be re-run later. A batch can be dismissed with a reason. Everything is audited.

**Frozen documents are flagged, not changed.** Open quotations (draft, pending, sent, approved) and active / draft price lists built on costings that use the changed input get a `ReviewFlag` ("Pipe: rate 98 → 105 (frozen prices on this document were not changed)") shown on the document and listed on the impact screen. At most one open flag per document and source; flags below the configured percentage threshold are not raised. Flags clear when the document is repriced, revised, or marked reviewed; they never block sending. Quotations and price lists are still marked out of date when their costing is reopened and re-approved (Phases 8–9).

**Impact report.** *Rate Change Impact* lists every batch (type, size of the change, live costings and documents affected, status) with its recorded results; the Phase 12 report "Rate change impact" shows the full rate history including the number of records each change affected.

**Not automatic by design.** Unit master factors, tax rules per state, and template edits do not trigger recalculation. Alerts are in-app only; there is no e-mail or message delivery yet.

## Phase 15: Settings and configuration
One **Settings** screen (`/settings`, `settings:view` to read, `settings:manage_settings` to change) gathers everything an administrator configures:
- **Company** (Phase 11): name, address, contact, GSTIN, currency code and symbol, footer note, logo. Print headers show "Amounts in INR (₹)".
- **Financial year and document numbers.** Start month of the financial year (default April) and a format for costing, quotation and price list numbers built from `{YYYY} {YY} {MM} {FY} {SEQ:n}` (exactly one `{SEQ}` required; letters, digits and `_ . / -` otherwise), with a restart rule: every calendar year, every financial year, or never. The screen previews the next number. The defaults reproduce the previous numbering (`COST-2026-0001`) and keep the old counters, so nothing restarts when you upgrade. If a format or restart rule is changed so that a number would repeat, the counter skips to the next free number instead of failing or duplicating.
- **Defaults for new documents.** GST %, wastage %, markup %, price list profit method and value, quotation validity days and terms, default product unit and dimension unit. They pre-fill new costings (from scratch), templates, quotations and price lists and can be changed on each document.
- **Printing.** Default paper (portrait / landscape) and default costing layout for the print previews.
- **Approval workflow.** Per costings and quotations: whether approval is required (costings: if not, an approver may approve a draft directly; quotations: if required, a draft cannot be sent before it is approved) and whether approvers may approve what they prepared themselves. Enforced on the server.
- **Calculation rules** (Phase 7): decimals, rounding, per-line rounding, GST included in rates, GST mode, wastage mode, markup base, profit base.
- **Rate update policy** (Phase 14): confirm / automatic / manual and the flag threshold.
- **Users, roles and permissions** link to the permission screens (Phase 2).

Storage: `AppSettings` holds one validated JSON document (shape: `appSettingsSchema` in `@costing/validators`); `GET /settings/defaults` serves the non-sensitive parts (defaults, print, approval flags, decimals) to every signed-in user. Settings missing from the stored document fall back to built-in defaults, so adding a setting later never breaks an installation, and a corrupt row falls back to the defaults instead of stopping the application. Changes are audited with the sections that changed.

## Phase 16: Testing and QA
Run everything with `pnpm test` (engine 137 tests, API 359). No test needs a database: Prisma is mocked, and schema/migration correctness is checked from the Prisma schema and by parsing every migration with the real PostgreSQL parser.

- **Route protection audit** (`apps/api/src/common/route-audit.spec.ts`). Walks every controller route in the real `AppModule` (including the generated master-data controllers). Fails if a route has no `@RequirePermission` unless it is listed there as signed-in-only or service-checked, with the reason; if a permission is not in the catalogue; if a data-changing route needs only a `view` permission; or if the public route list changes (sign-in, password reset, health, signed file links, customer quotation link). It also checks the starter roles against the real routes: Admin reaches everything; Accountant cannot administer users, roles, settings or imports; Staff can create costings but never approve, delete, change rates or administer.
- **Calculation edge cases** (`costing.edge.spec.ts`): empty and zero costings, binary-float traps (0.1 x 3, ten additions of 0.1), tiny and huge amounts, all four rounding modes, GST-inclusive rates, wastage extremes, every input-validation rejection, determinism and row-order independence. Alongside the existing seeded randomised invariants.
- **Document chain** (`workflow.spec.ts`): rates -> costing -> price -> quotation reconcile to the penny; a rate or labour change moves cost by exactly the difference; approved figures never move; minimum price, below-cost flag and GST-inclusive quoting.
- **Validators** (`apps/api/src/validation/validators.spec.ts`): money must be a decimal string (JS numbers are rejected), trimming, GSTIN, caps, cross-field rules, and that clients cannot set server-calculated money.

**Not covered by automated tests:** behaviour against a real PostgreSQL (CHECK constraints, partial indexes, migrations applied), browser/UI flows, and the look of Excel/PDF output. These need a database and a browser session and are the first items for the Phase 17/18 checks.

## Phase 17: Security and performance
**Sign-in.** After 5 failed attempts since the last good sign-in (15-minute window) an account refuses further attempts with HTTP 429, even with the right password; each blocked attempt is audited (`login_blocked`). Failures are counted from the audit log, so no schema change was needed. A password hash is always compared, also for unknown or inactive accounts, so response time does not reveal whether an account exists. (A locked response does reveal that an account exists; the IP throttle of 10 attempts a minute applies first.) New passwords need 8 to 128 characters with at least one letter and one digit; sign-in passwords and e-mails have length limits.

**Sessions.** The refresh token rotates on every use. If an already-rotated token is replayed more than 30 seconds later (a double click inside 30 seconds is harmless), the user is signed out of every session and `refresh_token_reuse` is audited.

**Production configuration** (`.env.example`): the API refuses to start in production without a random `JWT_SECRET` of at least 32 characters (placeholders rejected), without `WEB_ORIGIN` (the only CORS origin), and without a file-URL secret. API documentation (`/api/docs`) is off in production unless `ENABLE_SWAGGER=true`. `TRUST_PROXY=true` makes client IPs (throttling, lockout, audit) come from the reverse proxy. Request bodies are limited to 1 MB (uploads have their own limits), `X-Powered-By` is removed, helmet headers stay on.

**Limits against abuse and slow queries.** Page size is capped at 200 everywhere (the audit log list was unbounded). A costing or template is limited to 50 groups, 50 categories per group, 300 materials per category, 100 labour rows per group and 100 expenses; a price list to 500 items. Excel exports load at most 50,000 rows. Existing caps stay: 5,000 import rows, 5 MB uploads, 100,000 report source rows. For super administrators the permission catalogue is cached for 60 seconds instead of being read on every request.

**Checked and unchanged.** Every route has a permission or a documented exception (Phase 16 audit); passwords use bcrypt cost 12; refresh tokens and reset tokens are stored hashed; the refresh cookie is httpOnly, SameSite=Lax, Secure in production; uploaded images are re-encoded and served through signed links; all SQL goes through Prisma; the three raw queries are parameterised tagged templates with no user input concatenated.

**Not done:** no load test against a real database, no dependency vulnerability scan (needs registry access), no HTTPS/HSTS set-up (deployment phase), and password-reset links are still only written to the server log because there is no mail transport.

## Extension 2: Company expense and extra % (business extension, part 2 of 6)
**Company expense.** In the Expense master an administrator can tick *Company expense* (rent, admin overhead...). On every costing the **server** adds all active company expenses as locked rows (`CostingExpense.isCompany`), using the method, value and timing of the master; the browser shows them under "Company expenses" with a lock and cannot change or remove them. Anything a client sends for a company expense is ignored (it can neither be added twice nor altered). Templates do not carry them. They count as ordinary expenses in the maths (a percentage one is taken on material + labour; before/after GST as set) and are also summed separately into `Costing.companyExpenseCost` for the reports. Changing a company expense (value, method, timing, flag or active) is announced as a new recalculation kind `COMPANY_EXPENSE` that reaches **every** live costing through the existing Phase 14 workflow (batch, preview, confirm); approved costings keep the company rows they were approved with. Creating an active company expense, switching one on or off, and editing the flag, value, method or timing are all announced (found in the first live test: creation and activate/deactivate were not announced at first). Because every costing carries the rows, a used company expense cannot be deleted; deactivate it instead.

**Extra %.** A new header field *Extra %* (0-100, default 0) on the costing. `extraAmount = round(totalCostInclGst x extra / 100)`; the markup is then calculated on the uplifted cost (`total + extra`, or `basic + extra` when the markup base is basic cost), `sellingPrice = total + extra + markup`, and profit % is measured against the uplifted cost. With extra 0 every figure is exactly as before. It appears as its own line in the summary and the breakdown. Hand-checked example (reference sheet, GST 18 %, markup 10 %, extra 5 %): total 4868.82, extra 243.44, markup 511.23, selling 5623.49.

All of this lives in the costing engine (`extraPercent`, `isCompany`, results `extraAmount` and `companyExpenseCost`); the API only passes values through. Migration `20261116000000_company_expense_extra_percent` (new columns, CHECK 0-100 on the extra %, new `RecalcKind` value). Upgrade as in part 1: rebuild the images; no seed needed. Not yet run in the browser or on the live database.

## Extension 4: Dealer prices, publishing, cost report and the dealer price list
**Dealer prices.** When a costing is approved, `DealerPricesService.refresh` prices it for every active dealer from its saved figures with the engine's `calculateDealerPrice` (= `applyMargin` with the dealer's margin in place of the costing markup, then divided by the costing quantity): `CostingDealerPrice` keeps the margin used, markup, selling price (whole quantity, incl. GST) and unit price. A new dealer, a changed margin or switching a dealer on or off emits a `DEALER` change on the change bus and reprices that dealer's rows (no costing is recalculated). Reopening a costing takes it off the price list.

**Publishing.** `PATCH /costings/:id/publish` (`price_lists:approve`, approved costings only, audited; a database CHECK also refuses a published costing that is not approved). The **Cost Report** (`/cost-report`, `costing:view`) lists approved costings with basic cost, company expense, extra, markup, selling price and the publish tick. The **Dealer Price List** (`/price-list`, module `dealer_price_list`) shows published products with one unit-price column per dealer. Who sees which dealer: a user tied to dealers sees only those; anyone else sees all dealers only with `price_list_dealers:view`, so a dealer login created without a dealer sees nothing. The older price list documents (`/price-lists`) are unchanged.

**Tables.** Both pages use `components/data-table.tsx`: sorting, a filter under every column (text contains, number / date ranges, yes / no), search and paging all run on the server (`common/table-query.ts`, money compared as decimals); Excel exports use the same filters.

**Column access.** `TABLE_COLUMNS` in `packages/config` lists the columns of the costing list, cost report and dealer price list. Each column is a permission `column:<table>.<column>`, set per role (Roles page) and per user (allow / deny on the user page, *Column access* card). The server drops hidden columns from the response and the Excel export (`common/column-access.ts`) and refuses to sort or filter on them; super admins see every column. The seed gives each starter role its default columns of a table only while the role has none of that table's columns, so re-seeding never undoes an admin's choice.

**Designer.** Starter role *Designer* (module `images`). Costing photo routes accept `costing:edit` **or** the matching `images:*` permission (`@RequireAnyPermission`); a designer may change photos on approved and pending costings (photos never change figures; every change is audited). Page *Product Photos* (`/product-images`) lists products with name, code, status and photos only.

**Notifications.** `Notification` rows feed the bell in the header (checked every minute). When a published costing is added to, changed on or removed from a dealer's list, every active user tied to that dealer gets a message saying what changed ("was … now …"; the last price told is kept in `announcedUnitPrice`). Browser and phone push uses Web Push (`web-push`, VAPID keys from the environment): devices are registered from *My Profile*, stored in `PushSubscription` (https endpoints only, at most 10 per user, dead ones removed on 404 / 410). Push is sent after the change is saved and can never fail or undo it. The web app is installable (`app/manifest.ts`, `public/sw.js`, icons); push needs HTTPS, and on iPhone the app must be added to the Home Screen. Migration `20261119000000_notifications`.

**Starter roles added:** *Designer* and *Price List Dealer* (`dealer_price_list:view/export/print` only). Users without the dashboard start on the first page they may open.
